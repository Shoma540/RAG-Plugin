# 引継ぎ：My-Vault-RAG-Plugin（Obsidian の自作RAGプラグイン）2026-10-11版

## 0. この文書の使い方
- 読む人：設計役の Claude Code（セッション名 designer）。
- 役割分担：
  - designer（設計役）：作業の設計、作業役への指示の作成、作業役の報告の確認。ファイルの変更とコマンドの実行はしない（ファイルを読むことと、Web で調べることだけをする）。
  - worker（作業役）：designer から届いた指示どおりに作業し、報告を designer に送る。
  - Sho：designer の画面で、ルール3（A）の場合の回答と OK を出す。worker の画面で、ルール3（B）の操作の OK（1回だけ）と、許可の確認を押す。
- 作業の流れ：
  - designer が設計し、推奨どおりに SendMessage で @worker に指示を送る（Sho の OK は待たない）→ worker が作業し、報告を SendMessage で @designer に送る → designer が報告を確認する。
  - ただし「designer が守ること」のルール3（A）に当たる場合は、worker に指示を送る前に、designer の画面で Sho に聞き、OK をもらってから進める。
  - ルール3（B）の操作（お金がかかる可能性のある操作など）は、designer は Sho に聞かずに worker に依頼する。worker が自分の画面で Sho に直接確認し、Sho は worker の画面で1回だけ OK を出す。
  - designer は、1つのやること番号が終わるたび、またはルール3（A）の理由で designer の画面で Sho に聞くときに、次をまとめて Sho に報告する：決めたことと理由／worker にさせた作業／結果（確認できたこと／確認できていないこと）／呼んだ有料の API（なければ「なし」）／Sho がやる必要のあること（Obsidian の再起動など）。
- 詳しい仕様と経緯は、プラグインフォルダの CLAUDE.md（RAG本体の仕様書。末尾に変更履歴がある）と SUMMARY_NOTES.md（まとめノートの仕様書）に書いてある。
- この文書は、2026-10-10版の引継ぎ文（handoff\引継ぎ_2026-10-10.md）を置き換える。

## 3. 守るルール
### designer が守ること
1. 推測・推論で書かない。確かめていない事実には「未確認」と書く。
2. 新しい作業は、まず、理解した目的とゴール、不明点、各不明点の代替案と推奨を、番号で紐づけて理由付きで整理する。推奨は1つに絞る。ルール3（A）に当たらなければ、Sho の OK を待たずに推奨どおり worker に指示を送る。
3. Sho の OK は、次の2つの場合に、それぞれ決まった画面でもらう。
   - （A）designer の画面で Sho に聞く場合：worker に指示を送る前に、ルール2の整理を Sho に示し、OK をもらってから進める。
     - Sho にしか決められないこと（4-3・4-4・4-6 の判断、Obsidian での実機確認など）
     - 推奨を1つに絞れないとき、または判断の材料が足りないとき
   - （B）worker の画面で Sho が OK を出す操作：designer の画面では Sho に OK を求めず、そのまま worker に依頼する。worker が自分の画面で Sho に直接確認し、Sho は worker の画面で1回だけ OK を出す。
     - お金がかかる可能性のある操作（有料の API の呼び出しなど。料金がかからないことを公式の情報で確かめられない場合も含む）
     - ファイルやフォルダの削除
     - data.json の変更
     - ANSWER_SYSTEM_PROMPT（回答のルール。必須要件 R1・R3 に関わる）の変更
     - CLAUDE.md の書き換え
     - 依頼文には、Sho が worker の画面で判断できるように、何をするか・なぜ必要か・費用（分からなければ「公式の記載では未確認」）・元に戻せるかを書く。
     - data.json の変更を依頼するときは、「先に Obsidian を閉じてください」と Sho に伝えるよう、依頼文に書く。
4. 関数名・ファイル名・専門用語には、直後に括弧で中身の説明を付ける。会話を終わらせようとする締めの言葉は書かない。
5. worker の報告を確認するときは、確認できたことと確認できていないことを分けて Sho に書く。報告の事実は、必要ならファイルを読んで確かめる。

### worker への指示に必ず入れること
6. ビルドは CLAUDE.md に書かれたコマンドだけで行う。ほかのプラグインの main.js を上書きしない。
7. コードやテストを変更するときは、変更の前と後の両方でテストを流し、結果を比べて報告する。
8. お金がかかる可能性のある API（OpenAI・Claude・無料枠を外れた Gemini）を呼んだ場合は、呼んだ API・回数・トークン数・金額を報告する。呼んでいなければ「なし」と書く。
9. ファイルは BOM なし UTF-8 で保存する。元ノートは変更しない。APIキーの値は表示しない。テストのために作った値には「合成値」と書く。git のコミットはしない。
10. 作業前後の md5 の比較では、handoff\ フォルダも「変わってよいもの」として扱う。

### Sho が実機でやること
11. ビルドした後は、Obsidian を再起動する。
12. data.json を書き換えるときは、先に Obsidian を閉じる。
13. 索引（質問の検索に使うデータ）に反映されたかを質問で確かめるときは、まとめノートにだけあって元ノートには無い語句を使う。
14. ノートと質問に、個人情報や仕事上の機密を入れない（Gemini の無料枠では、送った内容が製品の改善に使われ、人が読むことがあるため）。入れるようになったら、その時点で Gemini の無料枠を使い続けるかを決め直す。

## 4. やること

### 4-1. まとめノートの自動やり直しを実機で確認する（Sho）
- いつ：元ノートが増えて「Vault RAG: まとめノートを更新」を実行し、作り直したまとめノートが前の版の50%未満の長さだったとき。わざと起こす必要はない。
- 確認すること：完了通知に「2回目で上書き」または「3回とも短すぎるため上書きせず」の行が出ること。上書きされなかったときに、summary-backup\{日付}\{チャンネル名}_候補.md が1つだけできること。
- 完了：上の表示を一度確認し、その結果を designer に伝えたとき。
- 注意：確認のためだけに、海外Yパパのまとめノートを作り直さない。今の版（32,215文字）より短い版でも、50%以上の長さがあれば上書きされてしまうため。

### 4-2. 大きいチャンネルのまとめノートを分割して作る方式を設計する（designer → worker）
- いつ：「まとめノートを更新」の確認画面で、どれかのチャンネルに「上限超過のため作成不可」と出たとき。
- なぜ：推定入力トークン数（本文の文字数×0.603）が data.json の summaryTokenBudgetPerMin（240,000）を超えるチャンネルは、今の仕組みでは作れない。Gemini 無料枠の上限は、1分あたり入力250,000トークン。
- 現状：いちばん大きいのは「海外Yパパラジオ　世界を読み解く」で、推定210,590トークン（10/3時点）。
- 決まっていないこと：元ノートをどう分けて送るか、分けて作った結果をどう1本にするか。
- 完了：そのチャンネルのまとめノートができ、完了通知の検証で形式違反が0件だったとき。
